# Cloudflare の約束事

D1・Workers・wrangler を使うときの決まり。
書き方の好みではなく、**守らないと壊れる・止まる・情報が漏れるもの**だけを書く。

## 1. D1

- D1 を読み書きする SQL は `#lib/server/db/`（`src/lib/server/db/`）の中にだけ書く。
  画面（`+page.server.ts` など）からは、そこにある関数だけを呼ぶ

- 値は必ずバインドする（`prepare(…).bind(…)`）。
  SQL の文字列に値をつなげない

- しおりに付くもの（予定・持ち物・立て替えなど）を読み書きする SQL には、必ず `trip_id = ?` を付ける。
  `trip_id` は、届いた札のハッシュから引いたものだけを使う。
  付けないと、1つのしおりのリンクを持つ人が、ID を変えてほかのしおりのものを直せるため

- ほかの行を指す列（幹事・足した人など）は、`(trip_id, 〜_id)` の複合の外部キーで、同じしおりの行だけを指せるようにする。
  アプリの確かめを1つ忘れても、テーブルでほかのしおりの行を指せないようにするため

- 2つ以上の書き込みは `env.DB.batch([...])` にまとめる。
  全部成功するか、全部失敗するかのどちらかになる。
  `BEGIN` などのトランザクションの SQL は D1 では使えない

- 保存するのは、使う人が「直す」「足す」などを押したときだけ。
  1文字打つごとに保存しない（1日の書き込みの上限に当たる）

- だれかが直したら、直した人の呼び名と、直す前の値を記録に残す。
  「変わった所」の表示と、まちがえて消したときに戻すのに使う

- 同時に直したときは、あとから保存した方が残る。
  ただし、紙を開いたあとでほかの人が同じものを先に直していたら、保存する前に「○○さんが、時刻を 9:00 → 9:30 に直していました」と出し、「○○さんの直しを残す」か「自分の直しで上書きする」かを選んでもらう（直すものに版の番号を持たせ、保存のときに比べる）

- D1 の上限（下の出典）に気をつける。
  特に、1つのクエリのバインド変数は 100 個まで。
  1回の実行で送れるクエリの本数と、1つのデータベースの大きさにも上限がある

- テーブルの形を変えるときは、`migrations/` に SQL を足し、`wrangler d1 migrations apply` で当てる。
  前の形のデータに当てても壊れないかを、テストで確かめてから当てる

- 親の表（`trips` など）を DROP して作り直すマイグレーションは書かない。
  D1 は外部キーを常に確かめていて、DROP の前の暗黙の DELETE で `ON DELETE CASCADE` が動き、子の表の行が全部消えるため。
  列を足す・表を足すで済ませる

- 全部の表を `STRICT` にする。
  数の列に文字が入ったり、主キーに NULL が入ったりするのを防ぐため

- 人を消す機能を作るときは、その人を指す列（足した人・幹事）を、同じ batch の中で先に UPDATE で外してから消す。
  複合の外部キーに `ON DELETE SET NULL` を付けると、`trip_id` まで NULL にしようとして止まるため

- データベース全体が壊れたとき（マイグレーションの失敗など）は、D1 の Time Travel（`wrangler d1 time-travel restore`）で戻す。
  無料プランで7日前まで、有料プランで30日前まで戻せる。
  戻るのはデータベース全体なので、1つのしおりの消しまちがいには使わない（画面の「元に戻す」で受ける）

## 2. しおりのリンク

- しおりの鍵は、推測されない乱数にする。
  `crypto.getRandomValues` で 128 ビット以上の乱数を作り、URL で使える文字にする。
  サーバーは、鍵から作った札のハッシュでしおりを見分ける

- 鍵は、リンクの `#` の後ろに置く（`https://dandori-san.com/s#<鍵>`）。
  `#` より後ろは、ブラウザがサーバーに送らない。
  鍵を使うのは端末の中だけにし、サーバーには一度も送らない。
  Cloudflare の記録と運営者に、鍵と中身が渡らないようにするため

- 端末の中で、鍵から HKDF で3つを別々に作る（`#lib/crypto/trip-crypto.ts`）。
  暗号の鍵（AES-GCM）と、呼び名を比べる鍵（HMAC）は、端末から出さない。
  サーバーに送るのは、しおりに入るための札（`accessToken`。32 バイト）だけにする。
  札は `Authorization` のヘッダーで送り、URL に入れない

- しおりの鍵だけでなく、全部の表の ID を、連番や作った時刻にしない。
  乱数にする（`#lib/crypto/random-id.ts`。JS の数のまま扱える 52 ビット）。
  ID の大きさから、作った時期や全体の件数が分かるため。
  ID は端末で作る（暗号にするときに行の ID が要るため）。
  ほかのしおりの ID を指せないことは、テーブルの複合の外部キーで守る（1章）

- リンクを知っている人は、だれでも見て書ける。
  リンクそのものが鍵の代わりなので、ログ・エラーの記録・コミット・PR・テストのデータに、本物のリンクと札を出さない

- D1 には、鍵も札も置かない。
  札の SHA-256（`access_hash`）を置き、届いた札をハッシュにしてから探す（`#lib/server/access.ts`）。
  D1 のデータが流出しても、そこから札を作れず、しおりを見たり書き換えたりできないようにするため。
  札は 128 ビット以上の乱数から作るので、パスワードのように遅いハッシュ（bcrypt など）は要らない

- 札の形に合わないものは、D1 を読む前に 401 にする。
  適当な札を試すボットのたびに、D1 を読んだりエラーのログを出したりしないため

- しおりの中身は、端末で暗号にしてからサーバーに送り、暗号文のまま D1 に置く（AES-GCM）。
  旅の名前・日にち・呼び名、これから足す予定・持ち物・立て替え・直した記録とその時刻も同じにする。
  サーバーと D1 には、だれが・いつ・どこへ行くかを読めないようにするため。
  D1 だけが流出したときに、使う人に知らせる必要が出るのを防ぐ（配る JS や札による書き換え、アカウントの乗っ取りは別）

- 中身の決まり（文字数・見えない文字・日にち）は、端末で確かめてから暗号にする（`#lib/trip-seal.ts`）。
  読んだあとも、端末でもう一度確かめる（[コードの約束事](code.md) 5章）。
  リンクを知る人は、わざと決まりに合わない中身も書き込めるため

- サーバーは中身を読めないので、送られた記録の形だけを確かめる（`#lib/trip-records.ts`）。
  暗号文の形と長さ、ID、HMAC の形、消す日の範囲（4章）を見る。
  D1 の関数は、届いた値を `unknown` で受け取って確かめる

- AES-GCM の追加データには、暗号の形の版・列の名前・行の ID・行の版の番号を入れる（`v1\0列\0行の ID\0版`）。
  同じしおりの中で、ほかの列やほかの行の暗号文に差し替えられたり、前の版の暗号文に戻されたりしても、読まないため。
  読めないときは、その欄を `null` にする（しおり全体は止めない。[コードの約束事](code.md) 5章）。
  列の名前は暗号の形の一部なので、D1 の列の名前を変えても、追加データの名前は変えない

- 直すときは、サーバーが版の番号を前の版＋1に決めて比べ、端末はその版の番号で暗号にする。
  前に読んだ暗号文を送り直されても、版が合わないので読めない

- 暗号にする前に、列ごとに決まった長さまで詰め物をする。
  暗号文の長さから、呼び名や旅の名前の文字数が分からないようにするため

- 暗号の形（HKDF の salt と info、追加データ、詰め物の長さ）を変えると、前のしおりが読めなくなる。
  鍵はどこにも無く、一度に作り直せないので、変えるときは版（`v1`）を上げ、前の版も読めるようにする。
  形は、Node の暗号の関数で別に作った暗号文を読むテストで固定している

- D1 を書き換えられる人は、中身を読めず、偽の中身も作れない。
  ただし、暗号文と版の番号を一緒に前の値に戻す（巻き戻す）ことまでは防げない。
  D1 の外に信用できる番号を持てないので、できないこととして受け入れる

- 暗号にしないのは、D1 が自分で使う値だけにする（ID、ほかの行を指す ID（`trip_id`・`organizer_id`・`added_by`）、札のハッシュ、消す日、版の番号、予定の番号、並び順の番号、呼び名の HMAC）。
  `added_by` からは、だれがだれを足したかが分かる。
  暗号にしない値に、時刻を持たせない。
  直した時刻や作った時刻があると、直しが増えた日から旅行の日が分かるため。
  並び順は、しおりの中だけの番号（`seq`）で決める

- 暗号文は毎回変わるので、同じ呼び名を断るときは、しおりごとの鍵で作った HMAC（`name_index`）で比べる。
  比べ方は [コードの約束事](code.md) 5章。
  読むときは、戻した呼び名の HMAC が `name_index` と合うかも確かめる。
  合わないときは止めずに印（`nameIndexMismatch`）を付ける（`name_index` だけを書き換えて、同じ呼び名を二重に入れられたのに気づくため）

- 暗号の鍵は、開かれたときに `#` の鍵から端末で毎回作る。
  鍵・暗号の鍵・札を、D1・ログ・環境変数・秘密の値のどこにも置かない

- 鍵を、端末の localStorage などにそのまま置かない。
  同じドメインのどこかに XSS があれば、全部の鍵が抜かれるため。
  置くなら、`extractable: false` の `CryptoKey` を IndexedDB に置く

- `history.replaceState` で `#` を消さない（読み直しやブックマークが壊れるため）。
  `/s` には `href="#…"` のページ内リンクを置かない（押すと鍵が消える）。
  「リンクを送る」の URL は `location.href` を使わず、手元の鍵から作り直す

- `crypto.subtle` は https でしか使えない。
  手元のスマホで、http の IP アドレスで開くと動かないので、実機で確かめるときは https で開く

- 段取りさんが作って配るリンク（「リンクを送る」と「みんなに知らせる」の文）には、`?openExternalBrowser=1` を `#` の前に付ける（`/s?openExternalBrowser=1#<鍵>`）。
  LINE で押されても、LINE の中のブラウザではなく、端末のふだんのブラウザで開くようにするため（名前などの保存が分かれず、ホーム画面にも足せる）。
  しおりのページは、この印が付いていても無くても同じに開く。
  LINE からふだんのブラウザに移るときに `#` の後ろが残るかは、iPhone と Android の実機で確かめる

- しおりの URL を、ほかのサイトに送らない。
  `Referrer-Policy: no-referrer` を返す（しおりの中の地図などのリンクを押したとき、Referer でしおりの URL が相手に渡るため）

- しおりのページは、検索エンジンに載せない。
  `X-Robots-Tag: noindex` を返す（だれかがリンクを公開の場所に貼っても、検索に出ないようにするため）

- しおりのページと、しおりのデータを返す応答には、`Cache-Control: private, no-store, no-transform` を返す。
  Worker の応答は CDN にキャッシュされないが、ブラウザ・途中の proxy・前のページに戻ったときのキャッシュに残さないため。
  `no-transform` は、Cloudflare 自身による応答の書き換え（スクリプトの差し込み）を止めるため

- URL・パス・`event.url`・`event.params`・リクエストのヘッダー（札が入る）・本文を、`console.*` やエラーの文に出さない。
  `handleError` は自分で書き、ルートの ID・エラーの名前・status だけを残す。
  SvelteKit の tracing は有効にしない（span に URL が入るため）

- GET では何も書かない。
  LINE などが、リンクの下見を作るためにページを取りに来るため

- すべての応答に、次のヘッダーを付ける。
  付けるのは `hooks.server.ts` の `handle` で、静的なファイルは Worker を通らないので、プロジェクトの直下の `_headers` にも書く
  - `Content-Security-Policy`：SvelteKit の `csp` の設定で作る。`default-src`・`script-src`・`style-src` は `'self'`、`img-src` は `'self'` と `data:`、`connect-src`・`form-action` は `'self'`、`base-uri`・`object-src`・`frame-ancestors` は `'none'`
  - `Strict-Transport-Security`・`Referrer-Policy: no-referrer`・`X-Content-Type-Options: nosniff`・`Permissions-Policy`（カメラ・マイク・位置などを切る）・`Cross-Origin-Opener-Policy: same-origin`・`Cross-Origin-Resource-Policy: same-origin`・`X-Frame-Options: DENY`

- XSS が1つあれば、`location.hash` から鍵が抜ける。
  止める手立ては、CSP の `script-src` を `'self'` にしぼることだけ。
  スクリプトが動けば、画面の移動・`window.open`・DNS の先読みで抜けるので、`connect-src`・`img-src` は、スクリプトの無い HTML の差し込みへの守りにすぎない

- zod は `z.config({ jitless: true })` にしてある（`#lib/trip-rules.ts`）。
  zod が `new Function` を試して、CSP の違反を出さないようにするため

- 受け入れる危険：運営者の配る JS が書き換えられると、端末で鍵を抜かれうる。
  Cloudflare か GitHub のアカウントを奪われたときや、依存パッケージに悪いコードが入ったときに起きる。
  そのため、Cloudflare・GitHub・npm のアカウントはハードウェアキーの2要素認証で守り、メンバーは自分だけにし、API トークンは最小の権限にして、公開用とマイグレーション用を分ける。
  依存パッケージの決まり（AGENTS.md）と CSP も、このために守る

- 受け入れる危険：鍵はリンクの一部なので、端末の履歴・ブックマーク・リンクを貼った LINE の中には残る。
  LINE はプレビューを作るためにリンクの文字を自分のサーバーに送る見込みが高く、ブラウザの履歴の同期・キーボードやクリップボードの同期・ブラウザの拡張にも渡りうる。
  リンクを鍵にする作りでは避けられない

- 受け入れる危険：リンクは取り消せない。
  グループを抜けた人や、リンクが漏れた先も、消える日まで読み書きできる。
  「リンクを作り直す」（新しい鍵で全部を暗号にし直し、`access_hash` と暗号文を1回の batch で入れ替える）は、あとで作る

## 3. 回数の上限

- しおりの作成と書き込みに、同じ相手から短い間に送れる回数の上限を設ける。
  大量に作られたり書き込まれたりして、ほかの人が使えなくなるのを防ぐ

- 上限を超えたときは、「少し待ってから、もう一度やってください」と出す

- 上限は、Workers の Rate Limiting（`wrangler.jsonc` の `ratelimits`）で作る。
  書き込みはしおりごと（札のハッシュ）に数え、しおりを作るのは IP で数える（作る人を見分ける手がかりが、ほかに無いため）。
  無料プランで使えるかは、作るときに確かめる

- Rate Limiting は Cloudflare の場所ごとに大まかに数え、期間も 10 秒か 60 秒しか選べない。
  いろいろな IP から少しずつ送られると、D1 の1日の上限を使い切られうる。
  そのため、API を作るときに、しおりごとの1日の書き込みの数を D1 の中に持って止め、しおりを作る数もサービス全体で1日いくつまでと決める。
  Turnstile を使うかは、人に確認する

- 札が合わなかった読み書きも、IP ごとに数える。
  札をあてずっぽうに試すボットに、D1 の1日の読み出しを使い切られないため

- IPv6 は /64 でまとめて数える（/64 の中で番地を変えるだけで逃れられるため）。
  日本の携帯回線は、多くの人が同じ IP を使うので、IP で数える上限はゆるめにする

- しおりごとに、足せる件数の上限を設ける。
  一緒に行く人は 50 人まで（`membersMaxCount`。超えたら `tooMany`）。
  予定・持ち物・立て替えにも、作るときに上限を付ける。
  リンクを知る人が足し続けて、D1 の1日の書き込みの上限と容量を使い切るのを防ぐため

- リクエストの本文は 16 KiB までにし、超えたら 413 を返す。
  `Content-Length` が無い POST は 411 を返す

- サイトを落とすほどの大量の通信（DDoS）は、Cloudflare がすべてのプランで防ぐ。
  段取りさんで作る上限は、その手前の、いたずらで書き込みを繰り返して D1 の1日の上限を使い切られるのを防ぐためのもの

## 4. 自動削除

- しおりは、旅行の最終日から3か月たったら消す。
  消す日は、最終日の3か月後の月の末日にする（3月10日 → 6月30日、11月30日 → 2月28日か29日、12月31日 → 3月31日）。
  消す日は暗号にできないので、最終日を逆算できないよう、月までにぼかす。
  そのため、3か月より最大で1か月ほど長く残る

- 消す日は、しおりを作ったときと、日にちを変えたときに、しおりに書いておく。
  日にちは暗号文でサーバーには読めないので、消す日は端末で計算して送る。
  サーバーは、月の末日か・今日より後か・今日の27か月後の月末までか、だけを確かめる（`deleteOnSchema`）

- 日にちを直すときは、消す日を前にずらす直しを断る（`changedDeleteOnSchema`）。
  今の消す日と、今日の3か月後の月末の、早い方より前にはしない。
  リンクを知る人に、旅行の前にしおりを消させないため

- 旅行の日にちは、日本時間の今日の1年前から2年後までにする（年は 2000〜2999）。
  終わりの日を遠い先にして、いつまでも消えないしおりを作られるのを防ぐため。
  終わってから3か月より前の旅行は、作った時点で消す日を過ぎているので、作るときに断る

- 消す日になったしおりは、Worker が消す前でも、消したものとして扱う（`findTrip` が `deleted` を返す）。
  Worker は1日1回なので、そのあいだに見たり書いたりできてしまうため

- 削除だけをする小さな Worker が、Cron で1日1回、消す日になったしおり（`delete_on <= 日本時間の今日`）と、それに付く予定・持ち物・立て替え・直した記録を、まとめて消す

- Cron の時刻は UTC で書く。
  日本時間の夜中の3時に動かすなら `0 18 * * *` にする

- 消したしおりは、札のハッシュと消した日だけを残す（`deleted_trips`）。
  消したしおりのリンクと、打ちまちがえたリンクを見分けるため。
  この印も、消した日から1年で消す

- 消したしおりと同じ札では、しおりを作り直せない（`createTrip` が `deleted` を返す）。
  古いリンクを押した人に、別の中身を見せないため

- 端末が作った ID がほかの行とぶつかったら、`idTaken` を返す。
  端末は ID を作り直して送り直す

- D1 の Time Travel には、消したしおりも、その期間（無料プランで7日、有料プランで30日）は残る

- 消したしおりのリンクを開いたら、「旅行が終わって3か月たったので、このしおりは消しました」と出す

## 5. 最新を取り直す

WebSocket を使わないので、次の3つのときに最新を取り直す。

- ページを開いたとき
- ほかのアプリやタブから戻ってきたとき（`visibilitychange`）
- 自分が書いたあと

旅行の当日だけ、画面が見えているあいだは、数分おきに「予定の番号」（`plansRevision`。[コードの約束事](code.md) 1章）だけを読み、変わっていたら画面の上に「ほかの人が予定を直しました」と「最新にする」を出す。

- 画面を勝手に入れ替えない（読んでいる途中の行がずれるため）。
  押したら取り直す

- 読むのは、しおりの「予定の番号」の1つだけにする。
  変わっていたときだけ、全部を取り直す

- 画面が隠れているあいだ（`document.hidden`）は確かめない。
  旅行の当日でなければ確かめない

- 読み上げには、まとめて1回だけ伝える（`aria-live="polite"`）

## 6. 電波がないとき

- SvelteKit の Service Worker で、画面のファイルと、最後に見たしおりを端末に保存する。
  電波がなくても、最後の状態は見られるようにする

- 最後に見たしおりは、サーバーから届いた暗号文のまま保存する。
  読むときに、`#` の鍵で端末の中で解く（読める形のしおりを、端末の保存データに残さないため）

- 電波がなくて最新を取れないときは、いつの状態かを画面に出す（例：「10:05 の時点のしおりです」）

- 電波がなくて保存できないときは、紙を閉じずに入力を残し、「電波がないので、保存できませんでした」と出す。
  あとで自動で送る仕組みは持たない（電波が戻るまでのあいだに、ほかの人の直しとぶつかりやすいため）

- iPhone の Safari は、7日間開かれなかったサイトの保存データ（呼び名・最後に見たしおり）を消す。
  旅行の前に開く人が多いと見て、今は案内しない。
  困る声が出たら、名前を入れる画面に案内を足す

## 7. wrangler の設定

- Cloudflare の設定は `wrangler.jsonc` に書く。
  ダッシュボードで変えたものは、`wrangler.jsonc` に書き戻す

- `observability`（ログ）・`traces`・`logpush` は、`wrangler.jsonc` で明示して切る。
  新しい Worker は、書かないとログが有効になり、札の入ったヘッダーや、しおりのパスと時刻を書き残すため

- 本番で `wrangler tail` を使わない。
  ヘッダー（札）が伏せられるかを確かめられていないため

- ゾーンの Web Analytics（自動の差し込み）・Zaraz・Rocket Loader・Email Obfuscation・Bot Fight Mode と JS Detections は、ダッシュボードで切る。
  `wrangler.jsonc` では切れない。
  どれも同じドメインのスクリプトとしてページに差し込まれ、XSS と同じように `#` の鍵を読めてしまうため。
  計測は、AGENTS.md の計測しない決まりにも反する

- D1 のデータベースは、最初に1回だけ `wrangler d1 create` で作り、出てきた ID を `wrangler.jsonc` に書く。
  ID を書かずに公開して、wrangler に自動で作らせない（D1 が二重にできる）

- 独自ドメインは、`wrangler.jsonc` の `routes`（`custom_domain: true`）で Worker に割り当てる。
  DNS のレコードと証明書は Cloudflare が自動で作るので、同じ名前の DNS レコードを手で作らない

- 独自ドメインの `routes` を足したら、`workers_dev: false` にする。
  workers.dev は、ゾーンの守り（WAF・HTTPS の強制など）を通らない2つ目の入り口になるため

- 問い合わせのアドレスは、Email Routing で `dandori-san.com` に作り、自分のメールに転送する。
  転送先の個人のアドレスは、画面・コード・`wrangler.jsonc`・PR のどこにも書かない（ダッシュボードで設定する）

- 個人情報の開示・訂正・利用停止などの請求と苦情には答える（個人情報保護法 32〜35・37・40条）。
  開示・訂正・消去は、しおりの画面で見る・直す・消すができるようにし、それを請求の手続にする。
  それ以外の問い合わせには、返事を約束しない

- 問い合わせの案内に、「しおりのリンクをメールで送らないでください」と書く。
  送られると、運営者が鍵を受け取ることになるため

- 問い合わせのメールは、暗号になっていない個人情報なので、残す期間を決めて消す（例：対応を終えてから決めた月数）。
  転送先の会社と国を、プライバシーポリシーに書く

- Cloudflare の側に残る記録（Security Events・Email Routing の記録など）は、運営者の手では消せない

- Cron は `triggers.crons` に書く。
  止めるときは `[]` にする（行を消したりコメントにしたりしても止まらない）

- 試験用の環境は `env.staging` で足す。
  D1 のつなぎ先などは、環境ごとに書き直す（親の設定から引き継がれない）

- 公開は GitHub Actions から行う。
  ワークフローは `push: main` だけで動かし、`environment: production` に承認者を付け、`permissions: {}` にする

- 公開用の API トークンは、要る権限だけにする。
  独自ドメインの `routes` を当てるには、Workers の編集に加えて、Workers Routes とゾーンの権限も要る見込み。
  作るときに要る権限を確かめて、ここを書き直す

- 秘密の値は `wrangler secret put` で入れる。
  `wrangler.jsonc` の `vars` に書かない（コミットされる）
